OUR CURRENT TECH STACK (for reference during the meeting)
---------------------------------------------------------------------------------------------------------
Language            Python 3.11
Data reading        pandas, openpyxl (Excel), pypdfium2 + pdfplumber (PDF), difflib (fuzzy name matching)
Data store          DuckDB (every row keeps its source file, sheet/page and row number)
Statistics          numpy: paired t-test (trend), Welch t-test (cause), correlation (links),
                    z-distance matching (finding a similar "twin" taluka). All rule-based, no AI.
AI (LLM)            Claude Sonnet 5.5 - "Messy-File Reader": maps messy column names to our standard fields
                                        (it sees only masked summaries, never school names or numbers)
                    Claude Sonnet 5.5 - "Brief Writer": writes the Marathi + English sentences, using placeholders
                                        such as {{n:id}}. Code fills in every number.
                    Claude Haiku 5.5  - "Intent parser": turns the officer's question into a plan
                                        (which taluka, which topic). Picks only from a fixed list.
Guardrails          Code verifier (no invented numbers, no causal words unless the evidence is STRONG,
                    no school names); one retry, then a fixed template. Recorded-answer cache;
                    spend cap; prompt-injection test.
Backend / UI        FastAPI + plain HTML/JS (Marathi/English, click any number to see its source)
PDF                 HTML -> PDF with headless Edge/Chrome (correct Devanagari)
WhatsApp            Meta WhatsApp Cloud API (webhook, signed messages, PDF reply)
Testing             pytest, 203 tests; an eval harness checks 8 planted truths across 5 synthetic datasets
Not built yet       Marathi speech-to-text, Marathi voice summary, officer file upload, deployment

Q1. SPEECH-TO-TEXT
Which speech-to-text model should we use for Marathi? We want something accurate on place names and numbers,
small enough to run cheaply, and free or open source if possible. Is Bhashini good enough, or should we
self-host?
---------------------------------------------------------------------------------------------------------
Our view:
- Shortlist:
  (a) AI4Bharat IndicConformer: open source, trained on Indian languages including Marathi, small
      (about 100-150M parameters), runs on a CPU or a small GPU.
  (b) Bhashini API (Government of India): free for registered users and uses AI4Bharat models behind the
      scenes, but depends on their uptime.
  (c) OpenAI Whisper large-v3 (about 1.5B parameters): open, but weaker on Marathi and heavier to run.
      AI4Bharat's Whisper versions fine-tuned on Indian languages are better.
- Speech-to-text does not use any LLM tokens. Only the short text question goes to Claude Haiku
  (about $0.0002 per question), so token cost is not the issue; accuracy and hosting cost are.
- Plan: IndicConformer as the main model, with the Bhashini API as a backup. Then "snap" the heard place
  name to our fixed taluka/school list, and ask the officer to confirm when unsure.
What we want from the mentor: Is this the right choice for real field audio (noise, dialects)?
Self-hosting vs Bhashini for a government deployment?

Q2. RAG IN THE LAST STAGE
Should we add RAG (retrieval) to the last stage, where the officer reads the Evidence Brief? For example,
so the officer can ask follow-up questions on the brief, or so actions can cite government guidelines.
---------------------------------------------------------------------------------------------------------
Our view:
- Numbers must never come from RAG. They are computed by code, which is our strongest guardrail.
- Follow-up questions on one brief ("which 11 schools?", "why is the election ruled out?") do not need a
  vector database. One evidence pack is small enough to give the LLM directly, and code still fills the
  numbers.
- RAG makes sense for documents: NIPUN Bharat guidelines, state government resolutions (GRs) and teacher
  transfer rules. The suggested actions could then quote the exact rule ("as per GR dated ..., the BEO
  can ..."), which makes the actions more trustworthy and realistic.
What we want from the mentor: Is RAG over policy documents worth it for the demo, or is it scope creep?
If yes, which simple setup (embeddings + a small local vector store) would he recommend?

Q3. DATA SIZE
How much data do we need? Is one block (about 100-140 schools x 5 years) enough to show real value, and how
big should our test sets be (officer questions, voice clips)?
---------------------------------------------------------------------------------------------------------
Our view:
- Correction to our own thinking: we are NOT training a model. We use ready-made AI models plus statistics,
  so "data size" means how much data the analysis needs to be trustworthy, plus how big our test sets are.
- Analysis: one block of 100-140 schools with 3-5 years of scores is enough for our tests. Our rules
  already refuse to conclude with fewer than 10 schools or too much missing data.
- Test sets: the 25 intent questions are too few. Target 100+ real questions written or spoken by
  officers, and about 150-200 voice clips from 6-8 officers in real settings.
- Scaling: the full Solapur district (about 2,800 schools) or the whole state is still small for DuckDB
  on one machine.
What we want from the mentor: Are these numbers convincing to judges? Should we prove scale on a bigger
synthetic district (e.g. a full district or 10 districts)?

Q5. INNOVATION (25%)
Is our main idea different enough from existing tools: "existing systems give officers data, Kaaran gives
them a data analyst" (cause testing, trust checks before conclusions, a "twin" taluka to learn from, and
evidence labels)? How should we present it so judges see the difference quickly?
---------------------------------------------------------------------------------------------------------
Our view:
- What is new compared with dashboards (UDISE+, VSK, PGI-D):
  - it answers "why", not "what";
  - it checks whether the data itself can be trusted first;
  - it tests several possible causes and rules some out;
  - it finds a similar taluka that improved;
  - it never lets the AI invent a number.
- Best way to show it: one 30-second side-by-side in the video. A dashboard shows "maths fell 3.3 points";
  Kaaran shows "11 schools without a maths teacher explain two-thirds of the fall, not the elections; 23
  attendance registers look fake; visit Malshiras, which improved".
What we want from the mentor: Does this land as novel, or does it look like "a dashboard with ChatGPT"?
What should we cut or highlight?

Q6. ARCHITECTURE FOR SCALE
Looking at our architecture (raw files -> ingest -> trust checks -> cause tester + twin finder -> evidence
pack -> AI writer -> verifier -> web / PDF / WhatsApp), what would you change to make it scalable and clean
for a real district or state rollout?
---------------------------------------------------------------------------------------------------------
Our view:
- Keep: the "evidence pack" contract in the middle. Engines produce it and the AI only reads it. This split
  is clean and easy to test.
- Change for scale:
  (1) a job queue (e.g. Redis + a worker) so long analyses and WhatsApp replies don't block the web server;
  (2) Postgres for users, questions and audit logs (who asked what, what was answered), with DuckDB kept
      for the analysis;
  (3) store each district's processed data once per upload, not per question;
  (4) logins and roles (DEO sees the district, BEO sees only their block);
  (5) a config file per state for column names and rules, so a new state needs no code changes.
What we want from the mentor: Which of these matter for the next stage, and is anything over-engineered
for now?

Q7. TECH STACK CHOICES
Is our stack the right choice (see the table at the top)? Specifically:
(a) Claude Sonnet/Haiku vs an Indian or open-source model (e.g. Sarvam, or Llama) for Marathi and for
    government data rules;
(b) numpy statistics vs a proper library (statsmodels) for credibility;
(c) plain HTML vs a framework for the UI.
---------------------------------------------------------------------------------------------------------
Our view:
- (a) Claude only sees aggregates (totals and averages, no names), and every number is filled in by code,
  so the model is replaceable. Our AI layer has one wrapper, so swapping the model is a small change.
  A government deployment may prefer an Indian or self-hosted model; we can run the same tests on it.
- (b) Moving the t-tests to statsmodels/scipy (and adding confidence intervals) would make the statistics
  easier for reviewers to trust, with little extra code.
- (c) Plain HTML is fast and light on low-end phones and slow networks; no change unless the mentor sees
  a real need.
What we want from the mentor: Would judges or a government client push back on a foreign closed model?
Is it worth showing a self-hosted fallback?

Q10. MEASURING SUCCESS AFTER A PILOT
What single measurable result would prove Kaaran is useful and should be scaled: time saved, number of
real problems caught, actions taken, or improvement in learning outcomes over time?
---------------------------------------------------------------------------------------------------------
Our view:
- Learning outcomes take a year to move, so they are too slow for a pilot.
- Within a pilot:
  (1) time to answer a "why" question (days -> under 5 minutes);
  (2) how many flagged problems are confirmed on field visits (e.g. fake attendance registers);
  (3) how many suggested actions are actually taken within a month;
  (4) whether officers keep using it without being reminded.
- (2) is the most convincing, because it shows Kaaran found something real that people did not know.
What we want from the mentor: Which metric would a DEO or a state official care about most?
